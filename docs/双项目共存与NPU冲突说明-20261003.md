# 双项目共存与NPU冲突说明

## 当前可用范围

- 项目一使用NPU检测，项目二使用CPU图文推理：真实短测已通过；小时级状态以补齐清单和对应result.json为准。
- 项目二单独使用NPU：真实文字、图片推理及常驻已验证；小时级测试正在补充。
- 项目一和项目二同时持有NPU模型：本板卡已复现驱动异常，不能宣称支持。

## 实测环境及证据

Orange Pi 5，Linux 6.1.99-rockchip-rk3588，RKNPU 0.9.8，系统报告内存7682.7 MiB。

项目一实际加载 `/lib/librknnrt.so`，版本2.3.0，SHA256 `73993ed4b440460825f21611731564503cc1d5a0c123746477da6cd574f34885`。

项目二加载自身私有RKNN 2.3.2，SHA256 `d31fc19c85b85f6091b2bd0f6af9d962d5264a4e410bfb536402ec92bac738e8`，配合已锁定的RKLLM SDK。版本差异是排查线索，尚无证据表明统一版本便能修复。

并行失败及请求级共享锁失败目录：板卡 `/path/to/project/data/joint-soak-20261003-122042-81530d`、`joint-soak-20261003-122738-374045`。发生推理超时、IOMMU域切换错误、DMA分配问题；重启后单独NPU和CPU/NPU共存恢复。

成功短测：`/path/to/project/data/joint-soak-20261003-130237-009102/result.json`。目标180秒，最终清理完成耗时200.407秒。项目一901帧、约5.004 FPS、零丢帧、3条已持久化告警；项目二51次请求（45文字、6视觉），3次事件ID与截图一致性检查，温度最高64.692°C。截图使用既有公开测试视频，不代表本轮测试过摄像头。

## 启动保护

新代码在 `/run/lock/rk3588-projects-npu.lock` 上持有整个模型上下文生命周期的锁：项目一共享锁，项目二NPU独占锁。冲突时在SDK初始化前明确失败，提示关闭另一个NPU会话或使用 `--cpu`。项目一的多路检测仍可共享模型运行。

锁由操作系统在进程退出时释放；不要删除锁文件来绕过保护。它只协调安装了该保护的两个项目，不管理第三方NPU程序。板卡以同一用户root运行；若换用户，需要先由管理员配置此锁文件的共同组权限，不要将目录改为任意用户可写。

它防止误启动触发已知故障，不能使双NPU并行变得可用。原来失败的逐请求串行方案已撤回，本次保护拒绝整个不兼容会话共存。

## 运行方式

项目一运行期间，板卡执行：

```bash
cd /path/to/project
bash scripts/board_console.sh --cpu
```

要使用项目二NPU，先正常停止项目一检测及其他项目二NPU会话，再执行：

```bash
cd /path/to/project
bash scripts/board_console.sh --npu
```

自动验证（互相不要同时运行）：

```bash
.venv-linux/bin/python scripts/check_joint_soak.py --mode npu-alone --seconds 3600
.venv-linux/bin/python scripts/check_joint_soak.py --mode cpu-joint --seconds 3600
```

## 后续底层排查依据

Rockchip内核仓库的[问题387](https://github.com/rockchip-linux/kernel/issues/387)报告了多IOMMU域、任务中止时的引用计数和域切换异常；相关[修复提案390](https://github.com/rockchip-linux/kernel/pull/390)仍需核对适用性。报告者是独立开发者，其内核为6.1.115，与本板卡不同。现象相似仅支持继续调查这一方向，不证明本板卡根因相同，也不等于厂商已经认可修复。

真正恢复双NPU支持需要：匹配本板卡驱动源代码，建立最小复现，验证上下文初始化/销毁与域切换行为，准备可恢复的测试系统后验证驱动修复，再做并行长稳。当前没有更换内核、替换系统RKNN库或安装未经本板验证的驱动。
